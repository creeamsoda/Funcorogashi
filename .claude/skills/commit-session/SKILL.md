# commit-session

このチャットセッション中に **あなた（Claude）自身が編集・作成したファイルだけ** をコミットするためのスキル。

ユーザーの作業ディレクトリには、あなたが触っていない変更（ユーザー自身の編集、他のツールが生成したファイルなど）が同居していることがある。`git add -A` や `git commit -a` を使うとそれらを巻き込んでしまうため、**必ず対象ファイルを明示的に指定してステージする**。

## 基本方針

- このセッションで自分が Edit / Write / その他のツールで変更・作成したファイルのパスを列挙する。会話の履歴を見返して、自分が触ったファイルを正確に把握すること。判断に迷うファイルはユーザーに確認する。
- ステージは `git add <明示パス>` で行い、`git add -A` / `git add .` / `git commit -a` は使わない。
- 自分が触っていない変更はステージせず、そのまま作業ツリーに残す。

## 手順

1. **自分の変更を特定する**
   - このセッションで自分が編集・作成したファイルのパスをリストアップする。
   - `git status` で現在の変更全体を確認し、そのうちどれが自分の担当分かを照合する。自分の担当外の変更が何件あるかも把握しておく（コミットに含めないことをユーザーに示すため）。

2. **対象ファイルだけをステージする**
   - パスを明示して `git add` する。パスにスペースや日本語が含まれる場合は引用符で囲む。
   ```bash
   git add "path/to/file1" "path/to/file2"
   ```

3. **ステージ内容を確認する**
   - `git status` で、意図したファイルだけが `Changes to be committed` に入り、自分の担当外の変更は `Changes not staged` に残っていることを確認する。想定と違えば止めてユーザーに報告する。

4. **コミットする**
   - コミットメッセージはセッションで行った変更内容を簡潔に表す。日本語プロジェクトなので日本語で書いてよい。
   - 現在のブランチが `main` / `master` などのデフォルトブランチの場合は、コミット前にユーザーへ確認する（別ブランチを切るべきか尋ねる）。
   - メッセージ末尾には必ず次の帰属行を付ける（セッションのモデル指定に従う）。
   ```bash
   git commit -m "$(cat <<'EOF'
   <変更内容の要約>

   Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
   EOF
   )"
   ```

5. **結果を報告する**
   - コミットしたファイルと、意図的に残した（コミットしなかった）変更をユーザーに伝える。

## やってはいけないこと

- `git add -A` / `git add .` / `git commit -a` で無差別にステージすること。
- 自分が触っていないファイルをコミットに含めること。
- `git reset --hard` や `git checkout -- <file>` など、コミットしない変更を破棄する操作。残す変更はあくまで作業ツリーに残すだけ。
- ユーザーが明示的に依頼していない `git push`。
